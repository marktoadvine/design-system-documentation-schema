# Conformance

This page defines what it means to conform to DSDS {{VERSION}} and lists every requirement the spec makes.

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** in the DSDS schemas and on this page follow [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) (as clarified by [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)). They carry weight only when written in upper case.

## Where the requirements live

DSDS puts its binding rules inside the schema `description` strings, next to the structures that enforce them. The schema *is* the specification. The index at the bottom of this page is generated from the schemas on every build so it stays current. Cite a requirement by its location-based ID (ex: `common/link§link.kind.1`). An ID only changes when the schema path it points to changes — that signals a citation needs re-checking.

## Conformance classes

DSDS defines four conformance classes. When claiming conformance, say which one applies.

### Conforming document

A JSON document that validates against the DSDS schema for the version its `dsdsVersion` declares, **and** passes the checks that JSON Schema alone cannot express. These are all the checks the reference implementation (`scripts/validate.js`) treats as errors:

- **Entity identifier uniqueness:** every entity `identifier` (every kind, including tokens, token groups, and nested token-group children) is unique across the whole document.
- **Entity-group identifier uniqueness:** group identifiers, when present, are unique among the groups.
- **Criterion identifier uniqueness:** within one entity, no two criteria share an `identifier`.
- **Section anchor uniqueness:** within one `sections` block, no two entries share an `anchor`.
- **Relationship integrity:** every `relationships[].target` resolves to a documented entity, no relationship points at its own entity, no duplicate relationships, and `composes`/`depends-on` stay acyclic.
- **Interaction component resolution:** every `interactions` `components[].identifier` resolves to a documented entity.
- **Checklist criterion resolution:** every checklist item's `criterion` resolves to a criterion defined on the same entity.
- **Variant constraint resolution:** every selection in a `variants` block's `exclusions` and `requirements` resolves to a flag or enum value defined in that block.
- **Token-layer resolution:** when the system documents a token layer, token-override maps (anatomy, states, variants) and string token references (`scaleStep.token`, theme overrides, motion entries) resolve to a documented token.
- **`tokenType` inheritance:** a token omits `tokenType` only when an ancestor token group declares it.
- **`docOrigin` block-key resolution:** every `metadata.docOrigin.blocks` key matches a block kind on the entity.
- **API platform uniqueness:** an entity declares at most one `api` block per platform.
- **Extension-key namespacing:** every `$extensions` key uses a vendor namespace.

One reference resolves against the assembled system rather than a single file, so it is **not** treated as an error here: `useCase.alternative.identifier` (the alternative may live in another file). Tools SHOULD resolve it when the full catalog is available.

Schema validity alone is not enough.

### Conforming producer

A tool or person that writes DSDS documents. A conforming producer:

- MUST emit conforming documents
- MUST NOT write deprecated forms in new output (a deprecated form exists only for reading old documents, never for writing new ones — as of 0.14.0, nothing is deprecated)
- SHOULD record how the documentation was produced, via the `docOrigin` metadata field

### Conforming consumer

A tool, renderer, or agent that reads DSDS documents. A conforming consumer:

- MUST NOT fail on optional fields it doesn't recognize
- MUST preserve `$extensions` data it doesn't understand
- MUST treat unresolvable references as defects, not silently drop them
- MUST respect RFC 2119 levels on guidance it acts on (a `must-not` guideline is a hard requirement for an agent writing code)

### Conforming validator

A tool that checks documents. A conforming validator MUST enforce both the structural layer (the JSON Schema, with format assertion enabled) and the semantic layer. It SHOULD also surface the lint layer (the rules catalog in `rules/rules.yaml`) as warnings. The reference implementation is `scripts/validate.js`. Its test fixtures in `test/invalid/` pin every check and work as a test suite for independent validators.

## Enforcement tiers

Every requirement falls into one of three tiers, or is advisory:

| Tier | Mechanism | Failure mode |
|---|---|---|
| Structural | JSON Schema (patterns, required, minItems, conditionals) | Validation error |
| Semantic | Reference implementation checks (resolution, uniqueness, inheritance, cycles) | Validation error |
| Lint | Rules catalog (`rules/rules.yaml`, DSDS-001…) | Warning — never a validation error |
| Advisory | SHOULD/MAY statements consumed by judgment | None |

#### metadata/category

- **MUST:** MUST be lowercase kebab-case. <small>`metadata/category§category.1`</small>

#### metadata/doc-origin

- **SHOULD:** For API accuracy, agents SHOULD prefer 'generated' or 'extracted'. <small>`metadata/doc-origin§docOriginValue.1`</small>

#### metadata/governance

- **SHOULD:** A named person goes stale the moment they leave, so wwners SHOULD be teams, roles, or group aliases ('Design Systems', '@acme/design-system'). <small>`metadata/governance§owner.1`</small>
- **SHOULD:** Tools SHOULD show the owner wherever a reader might need to flag a problem. <small>`metadata/governance§owner.2`</small>
- **SHOULD:** SHOULD name a team or role, not an individual. <small>`metadata/governance§owner[oneOf][1].name.1`</small>
- **SHOULD:** Tools SHOULD link it when it parses as a URL or email. <small>`metadata/governance§owner[oneOf][1].contact.1`</small>
- **MAY:** Tools MAY treat an old or missing `lastReviewed` as a staleness signal. <small>`metadata/governance§lastReviewed.1`</small>

- **MUST NOT:** MUST NOT contain markup. <small>`metadata/governance§lastReviewed[oneOf][1].note.1`</small>
- **MAY:** If the code has moved past this version, the doc MAY be stale even if recently reviewed. <small>`metadata/governance§lastReviewed[oneOf][1].reviewedAgainst.1`</small>
- **SHOULD:** `lastReviewed` is optional but SHOULD be set once you have a review process. <small>`metadata/governance§governance.1`</small>

#### metadata/last-updated
