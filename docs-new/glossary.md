# Glossary

Terms this spec uses with a specific, load-bearing meaning — not generic JSON Schema vocabulary. Alphabetical.

**Combo** — the shared rule shape (`common/combo.schema.yaml`) for "these things do or don't go together": a `subject` (a trait selection, a token reference, or another entry's id), a `level` (`common/requirement-level.schema.yaml`) saying whether `items` is the permitted set or the forbidden set and how strict that is, and `items` (bare target strings). Used in two places: a component's own top-level `combos` array (which of its variants/states/flags must or must never coexist), and a token entry's own top-level `combos` (which other tokens this one has actually been verified against). Not its own section kind - a combo rule is a structural fact about a specific trait or token, not a piece of documentation in its own right, so it lives directly on the thing it's about instead of in a free-floating section a reader has to cross-reference by string id.

**$comment** — the JSON Schema annotation keyword this spec uses, at the property level, for *how, when, or why* to use a property - never validated, never shown to an end reader. Paired with `description`, which says what the property *is*. Added only when there's real guidance beyond the obvious; most properties don't need one.

**$extensions** — the escape hatch for tool-specific data, present on `entry`, `section`, and the base document. Keyed by a reverse-DNS-style namespace (e.g. `com.figma`), freeform underneath. A Figma plugin, a Storybook addon, etc. can stash data here without needing a schema change, and the namespaced key keeps two tools' data from colliding.

**Definitions** — a section kind holding term definitions: what a term means, how and when to use it, and related terms it's often confused with. Renamed from `glossary`, to avoid colliding with this spec's own glossary.md - a section on an entry defines that entry's own terms, not this spec's vocabulary. Distinct from `Metadata`'s `tags` (classification keywords) - a definitions entry is a definition, not a label.

**Description** — the field name for text that says what its parent thing *is*, always. A plain string at the top level (entry, section) - the "only place to say what this is," kept short so it can't turn into a place to bury real documentation - or `common/markdown.schema.yaml` everywhere else (a component's own `traits` item, a step, a definition), where more explanatory prose is expected. Kept distinct from `Note`, which is a record *about* the parent, not what defines it. A guideline's own claim uses `statement` instead, and a `freeform` entry's own content uses `body` instead, since "description" is reserved for this narrower, defining role, not for substantive standalone content. The schema's own JSON Schema `description` keyword on each property follows the same split, one level down: concisely says what the property represents, paired with `$comment` for how/when/why to use it (see `$comment`).

**Entry** — one thing in the design system graph: a system, component, token, theme, or the generic `entry` kind for anything else. Renamed from `node`, which was itself renamed from `entity`. An entry's own file is just one serialization of it; `refs` are its edges to other entries.

**Entry kinds** — the five values an entry's `kind` can take: `system`, `component`, `token`, `theme`, `entry`. Four (`system`, `component`, `token`, `theme`) have their own `entries/<kind>.schema.yaml` file, extending the shared open base (`entry.schema.yaml`) and closing it with a `const` `kind` plus whatever's only meaningful for that kind. The fifth, `entry`, is the explicit generic kind - no fields of its own, checked against `entry.schema.yaml` directly, the same fallback a custom (dotted, namespaced) kind gets. `element`, `pattern`, and `manual` briefly lived here as three separate fileless values before being consolidated into the one generic `entry`, since all three were checked identically. There is no `token-group` kind - grouping tokens is a `metadata.group` fact, not a second artifact wrapping them (see `Group`).

**For** — `human`, `agent`, or `all`. A required field on every section, saying who it's written for. Replaces the old `documentBlocks` / `agentDocumentBlocks` split (two separate arrays) with one tag on a shared array. Renamed from `audience` - shorter, and reads directly in place ("for: agent") rather than needing translation ("audience: agent" means "for an agent"). The enum's third value is `all`, not `both` - several example documents lagged behind this rename until it was caught and fixed.

**Freeform** — `section.freeform`, an optional array of headed, arbitrarily-nested sub-content available on every section kind (typically used for long-form narrative structure — installation steps, background reading, etc.), alongside that kind's own structured `items`. Used to be its own section kind; folded onto `section.schema.yaml`'s own base once every kind needed the option to carry it, the same way `entry.schema.yaml`'s `sections` and `metadata.schema.yaml`'s own fields are available unconditionally rather than gated per kind. Renamed twice before that: `sections` → `slots` (to free that word up for the overarching concept once `document-blocks/` became `sections/`) → `freeform` ("slot" reads like a named placeholder a template fills in, not "flexible, unstructured content" - the opposite of what this holds).

**Group** — `metadata.group`, a group name an entry belongs to (for example `color.action` on a set of related tokens). The recommended way to group tokens; there is no separate `token-group` entry kind, since a group is a fact about its members, not a second artifact wrapping them.

**Guidelines** — a section kind holding rules for an entry: how to build it, or (when the section's own `context` is `when-to-use`) when it's the right choice at all. Every item pairs a `statement` with a `level`.

**Id** — the one identifier shape in this spec (`common/id.schema.yaml`), lowercase-dash segments optionally dot-chained (e.g. `color.action.primary`). Used both for an entry's own globally-unique `id` and for flat, locally-scoped ids on section items (a guideline's `id`, a `freeform` entry's `id`) — one pattern, no second concept for "a shorter kind of id." `freeform` used to call its own version `anchor`; renamed so every connectable item uses the same field name.

**Item** — the one universal box a section's content lives in. Every section kind has an `items` array and puts everything there, never under a kind-specific key like `parts`/`steps`/`properties` — what an item actually contains depends entirely on the section's `kind`.

**Kind** — the one discriminator field name used at every level of this spec: on every entry and every section, naming which shape applies. Entry's own discriminator used to be called `type`; unified to `kind` rather than the other way around because `type` is already overloaded elsewhere (the JSON Schema keyword itself). See also `Part` for the equivalent one level down, inside a component's own `traits`.

**Metadata** — minor/optional facts about an entry that aren't documentation and aren't pointers to other entries. Split into a base shape (`metadata.schema.yaml`: `tags`, `owner`, `reviewed`, `context`, `updated`, `origin`) every entry uses, and per-kind extensions that add more: `entry-metadata.schema.yaml` (adds `status`, `since`, `group`, `aliases`, `preview` - used by every entry kind) and `system-metadata.schema.yaml` (adds `version`, `organization`, `url`, `license`, `platforms` - used only by a `kind: system` entry).

**Name** — the field name for a thing's human-readable identifier, always paired with a machine-readable `id` (an entry's own `name`, a `shared` entry's `name`, a component's own `traits` item `name`). The display counterpart to `id`, not a heading - use `Title` for a heading over content that isn't itself an identified artifact. `base.schema.yaml`'s document-level `name` is the one exception with no sibling `id` (a base document has none), but it still names the design system as a whole rather than heading a piece of content, so `name` is still the right fit.

**Note** — the field name for a supplementary record or annotation *about* its parent, never what defines the parent (that's `Description`). Always a plain string, never markdown - a note is a brief aside, not documentation. Appears on `common/ref` (context about a specific connection), `common/showcase` (extra detail about a visual sample), `common/combo` (why a pairing rule holds, when the rule's `subject`/`level`/`items` already say what it is), and `metadata`'s `reviewed`/`updated`/`origin` sub-objects (a plain-text aside on that record). If a field would hold the actual substance of what its parent is or says, it isn't a `note` - use `description`, `statement`, or `body` instead.

**Origin** — `metadata.origin`, how an entry's documentation came to exist and who or what wrote it: `method` (`authored`/`generated`/`extracted`/`reconstructed`) and `author` (`human`/`ai-assisted`/`ai-generated`/`machine-assisted`/`machine-generated`). Renamed from `docOrigin`; its own `overall`/`authorship` fields renamed to `method`/`author`.

**Owner** — `metadata.owner`, the team, role, or person accountable for an entry, as a plain mailbox-style string. Renamed from the old `governance.owner` object wrapper, once `governance` turned out to be a one-field wrapper around what is now `owner` plus the sibling `reviewed` field.

**Part** — a per-item discriminator inside an array that can hold more than one distinct shape (used in a component's own `traits`). Plays the same role one level down that a section's own `kind` plays for the section itself. Renamed from `facet`.

**Platform** — an id naming a target platform/framework (`react`, `ios`, etc.), used on a `status` entry, a component's own `sourceFiles`/`imports` entries. A `kind: system` entry's `metadata.platforms` is the full registry: a bare array of platform ids, nothing else - when present, every other `platform` value anywhere in the document must match one of its entries — checked by `tools/validate.js`, not the schema alone. There is no base-level `platforms` field; it lives on the system entry's metadata, the same shape every entry's metadata uses.

**Purpose** — why something exists or holds, on a component's own `traits` item. Renamed from `reason`, which was itself renamed from `rationale` - each pass shortened the word without changing what it means: markdown prose citing evidence, a standard, or a past incident.

**Ref** — the one pointer type in this spec (`common/ref.schema.yaml`): `{rel, to|href, ...}`. Replaces four separate earlier pointer shapes (link, relationship, extends, entity-ref). `to` addresses something inside this document's own graph (an entry, or an entry#item); `href` addresses something outside it (a file, a URL, a package) - exactly one of the two is given. `rel` says what kind of pointer it is. Always held in a field called `refs` when it's an array - `freeform` entries briefly called theirs `links` instead (a leftover from before `ref` unified everything); renamed to match.

**Rel** — the field on a `ref` naming the relationship (`depends-on`, `composes`, `part-of`, `alternative-to`, `extends`, `refines`, `lint-rule`, `test`, `file`, `source`, `design`, `storybook`, `package`, `external-link`, `pairs-with`, `excludes`, or a namespaced custom value like `acme.supersedes`).

**Reviewed** — `metadata.reviewed`, when a person last confirmed an entry's documentation was accurate: `date`, `by`, and `note`. Renamed from the old `governance.lastReviewed`.

**Base document** — a file with a top-level `schemaVersion` key. Holds `entries` (always an array, even for one), optional `shared` content, and its own `refs`/`$extensions`. System-wide facts and documentation live on that list's own `kind: system` entry, not on the base document directly - there is no base-level `metadata` or `sections` field.

**Section** — one piece of an entry's documentation: a typed container tagged by who it's `for`, whose content always lives in `items` and/or `freeform` (never a kind-specific key). Renamed from `block`. `definitions`, `guidelines`, and `steps` each extend `sections/section.schema.yaml` with their own file; the generic `section` kind is checked against that base directly, the same fallback `entry` gets on the entry side.

**Statement** — the actual claim text on a guideline item (or, informally, the same idea wherever a field holds "the rule/scenario in words" — e.g. a guideline's `statement`, which doubles as "the user's situation" inside a "when to use" guidelines section).

**Status** — a lifecycle value (`stable`, `deprecated`, `beta`, etc.), optionally scoped to one platform. Lives in `metadata.status`, always a single object: a `status` word, plus optionally the one `platform` it applies to, `since`, `deprecationNotice` (required when `status` is `deprecated`), and `note`. There is no bare-string or array shorthand - a status entry never covers more than one platform at a time. Optional: nothing else in this spec structurally depends on an entry's status being present.

**System** — the entry kind for the design system as a whole (`entries/system.schema.yaml`). Carries system-wide `metadata` (`version`, `organization`, `url`, `license`, `platforms`) and system-wide `sections`, the same shapes every entry already has, instead of a bespoke base-level shape. A base document is not itself a system entry - it's the envelope (`schemaVersion`, `name`, `entries`, `shared`, `refs`) that holds one.

**Tags** — freeform classification keywords on `metadata`, for grouping/search/filtering. By convention the first tag, if any, is the primary/nav category.

**Title** — the one word this spec uses for a short heading describing a subject, consistently: a section's own optional `title`, a `freeform` entry's required `title`, a `steps` entry's required `title` (renamed from upstream's `label`, which duplicated this same role under a different name), and a `common/example`'s own optional `title` (renamed from `name` - an example isn't an identified artifact with a paired `id`, it's a piece of content with a heading, the same role `title` plays everywhere else). Always a plain string, not markdown. Distinct from `Name`, the human-readable counterpart to a machine-readable `id` - a different pairing, not a heading.

**Token overrides** — a map of purpose-name → token reference (e.g. `{background: "{color.action.primary}"}"`), used inside a component's own `traits` entries to say which token fills which visual role. Distinct from a `ref` (which points at a whole other entry). Also distinct from what a `theme` entry changes: that's not enumerated in this spec at all - a theme's own `source` field names its real DTCG source file, and the tokens it actually overrides are whichever that source redeclares.

**Traits** — a component-only field for every way it can vary: an on/off dimension (`boolean`, whether the consumer sets it or it happens on its own at runtime - `description` says which) or a set of named options (`enum`), tagged per entry by `kind`. Not a section kind - it lives directly on `entries/component.schema.yaml`, alongside `combos`, `imports`, and `sourceFiles`, since these are structural facts about a component specifically, not general-purpose documentation content any entry kind might carry. Renamed from `modes` - too easily misread next to `node`, same length, one letter apart (the rename predates `node` itself being renamed to `entry`).
